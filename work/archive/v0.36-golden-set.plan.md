# cage-lab golden set — a driven, real, reproducible capture corpus

**Plan of record** for `../cage-lab/golden/`. Detail doc; summarized in
[PLAN.md](PLAN.md) §11 alongside the lab plan
([cage-lab-plan.md](cage-lab-plan.md), whose §2.1 zero-mock law this satisfies
*better* than the sample set does).

**The idea (Arpit, 2026-07-25):** stop hoping the right situations appear in
ad-hoc logs. **Drive the real agents ourselves** with a curated question set,
capture exactly what each one writes to disk, and freeze that as the **golden
set** — real files, known provenance, deliberately covering every capture
dimension cage claims to measure.

**Two payoffs, and the first one is the bigger one:**

1. **Discovery** — a per-surface, per-field truth table of what each agent
   *actually* logs (does Kiro ever write output tokens? does Copilot CLI record
   cache reads? where does the VS Code title really live?). That tells us what
   cage can honestly build, and where a metric is structurally impossible.
2. **Golden inputs** — the M/G matrix in [cage-lab-plan.md](cage-lab-plan.md) §3
   stops depending on whatever happened to be in `samples/` and runs on a corpus
   that covers every dimension on purpose.

**A property worth naming:** because *we* author the questions, the transcripts
contain no private content — so golden captures are frozen **byte-exact, no
stripping**, unlike `samples/**` (which had content removed). This is the most
real input cage will ever be tested against.

## 1. Layout

```
../cage-lab/golden/
  README.md                  # how to run a session, what gets captured
  drive.py                   # the CLI driver (claude · copilot · kiro)
  questions/
    core.toml                # the question set (§3) — id, prompt, dimension, expectations
    graphify.toml            # the graphify A/B pairs (§4)
  manual/
    vscode-checklist.md      # the human-run VS Code/IDE script (§5)
    _template.md             # per-run record Arpit fills in (ids, timings, notes)
  captures/
    <run-id>/                # run-id = YYYYMMDD-HHMM-<agent>-<surface>-<graphify?>
      manifest.json          # provenance: agent, version, surface, cwd, questions asked,
                             #   session ids, file paths, sha256, capture window,
                             #   + which config file was active (cage.toml | policy.toml
                             #     fallback) and any coexisting legacy file — §2.7
      logs/                  # the agent's own log files, copied VERBATIM
      ledger/                # the .cage produced by importing them (for reference)
      transcript-map.json    # question id → session id → the log lines it produced
  findings/
    field-matrix.md          # THE deliverable: agent × surface × field truth table (§6)
    field-matrix.json
```

Golden captures are **committed** to cage-lab (small, content-safe, and the
whole point is that they're frozen). `captures/` is append-only: a new run never
overwrites an old one — a format change should show up as a *diff between runs*.

## 2. The driver (`drive.py`)

Stdlib-only. One session per invocation, fully recorded.

```bash
python golden/drive.py --agent claude  --set core          # a full core run
python golden/drive.py --agent copilot --set core --graphify on
python golden/drive.py --agent kiro    --only Q3,Q7        # targeted top-up
python golden/drive.py --list                              # questions + dimensions
```

Protocol per run — the part that makes captures trustworthy:

1. **Pre-snapshot.** Record the agent's log dir listing + per-file size/mtime/sha
   *before* anything runs, so the run's own output is provably isolated.
2. **Fresh working dir.** A scratch git repo (a small fixed codebase checked into
   `golden/workspace/` so answers are stable across runs), its own cwd — this is
   what `project`/`scope` will pick up.
3. **Ask** each question through the agent's real CLI, one turn at a time,
   honoring the question's `pause_before` (that's what creates real `gap_ms`).
4. **Post-snapshot + diff** → exactly which files the run touched.
5. **Copy verbatim** every new/changed log file into `captures/<run-id>/logs/`,
   preserving relative structure; record sha256 of both source and copy.
6. **Import into a scratch ledger** (`captures/<run-id>/ledger/`) so the golden
   set ships with cage's interpretation *alongside* the raw truth — useful for
   diffing behavior across cage versions later.
7. **Write `manifest.json` + `transcript-map.json`.** Map question id → session id
   → the specific log lines/records it produced. This is what makes a golden
   capture *checkable by eye*: you can point at a question and see its bytes.
8. **Never edit a captured byte.** Sanitization is unnecessary by construction
   (§0) and forbidden by rule.

If an agent CLI isn't installed, the run records `NOT AVAILABLE — <agent> CLI not
installed` and exits 0 — a gap is reported, never simulated.

## 2.4a Workspace provenance — a workspace is evidence only if reproducible (2026-07-28)

**Standing rule, learned the hard way.** The first `golden/workspace/` had a real
`graphify-out/` graph and cage's interceptor shim, but **no record of how it was
built** — and `graphify claude install` had never been run. So the graphify A/B
measured a half-configured condition nobody could reproduce, and the resulting
finding over-claimed (see
[graphify-ab-steering.plan.md](graphify-ab-steering.plan.md)).

Therefore:

- Every workspace carries **`SETUP.md` + a re-runnable `rebuild.sh`** listing the
  exact commands **and their order** that produced it.
- **Use each tool's own installer**, never a hand-written equivalent —
  `graphify claude install`, `cage setup --<agent>` — so the workspace reproduces
  what a real user gets rather than what we guessed they'd get.
- **Record what each installer did to shared files.** `graphify claude install`
  and `cage setup` both write `CLAUDE.md`; which one clobbers the other's block is
  a real observation, not a detail.
- Verify, don't assume: `cage doctor` must report the interceptor **live**, and
  the agent integration must be **present**, before any cell runs.
- **A capture taken against an unreproducible workspace is downgraded to
  UNPROVEN** — the same standard the benchmark applies to everything else.

## 2.5 The three phases (Arpit, 2026-07-25) — validate before you bulk-run

Each phase is separately validatable and **gates the next**. A protocol flaw
found in a full sweep costs ~100 real LLM calls *and* freezes itself into every
capture, so nothing bulk happens until Phase 1 is signed off.

### Phase 1 — setup + capture validation across EVERY surface (gating)

Goal: prove that **for every agent × surface × graphify state, capture happens
and the numbers are right.** Small question count, full breadth.

**Setup first:**

- `golden/` scaffolded, `drive.py` protocol implemented (§2), frozen
  `golden/workspace/` committed.
- **Graphify interceptor wired** into the workspace (`cage setup` writes
  `bin/graphify` + PATH) so the ON runs actually route through it — and verified
  live (`cage doctor` reports the interceptor healthy, not just present; the
  liveness check exists because a dead shim silently exec's the real binary).
- **Config baseline recorded** — `cage setup` scaffolds `cage.toml` (v0.36,
  §2.7); the run notes which config file is active and that no stray legacy
  `policy.toml` is shadowing it.

**The validation matrix — 2–4 questions per cell, not 18:**

| cell | surface | graphify | driven how |
|---|---|---|---|
| V1 | claude **CLI** | off | script |
| V2 | claude **CLI** | on | script |
| V3 | copilot **CLI** | off | script |
| V4 | copilot **CLI** | on | script |
| V5 | kiro **CLI** | off | script — **Kiro CLI exists** (`kiro-cli chat --no-interactive`, §2.6); this cell is real, and its first job is *discovering where it logs* |
| V5b | kiro **CLI** | on | script |
| V6 | claude **VS Code** | off | **manual** (Arpit) |
| V7 | claude **VS Code** | on | **manual** |
| V8 | copilot **VS Code** | off | **manual** |
| V9 | copilot **VS Code** | on | **manual** |
| V10 | kiro **IDE** | off | **manual** |
| V11 | kiro **IDE** | on | **manual** |

Questions per cell: **Q1** (floor), **Q2 → Q3** (cache create + read), and for
the graphify-ON cells one architecture question from §4 so a saving is actually
produced. Total ≈ 35–45 real calls — a fraction of a full sweep.

**Driving commands (non-interactive, one turn each):**

| agent | command |
|---|---|
| claude | `claude -p "<question>"` (verify the flag on the installed version) |
| copilot | the Copilot CLI's non-interactive form (verify on the installed version) |
| kiro | `kiro-cli chat --no-interactive "<question>"` (documented, §2.6) |

The driver must confirm each agent's own non-interactive invocation from
`--help` at run time rather than trusting this table — CLI flags move.

**The seven checks, applied to every cell:**

1. **Snapshot diff is exact** — the post-run diff names precisely the files that
   session touched: no misses, no unrelated churn.
2. **Copy is faithful** — sha256 of each copied log equals its source, and the
   source's sha is unchanged from before the run (we only ever read).
3. **Question → bytes mapping works** — `transcript-map.json` points each
   question at the specific log records it produced; opening the log at those
   lines shows the expected turn.
4. **Import is complete** — `cage import --path <captured log>` produces exactly
   the expected number of call rows (hand-counted from the log).
5. **Values reconcile three ways** — the log's numbers = cage's ledger row = the
   lab's independent recount. Any drift stops everything: it means capture or
   accounting is wrong, which is the whole reason cage exists.
6. **Derived signals appear where they should** — `cache_write_in` on Q2,
   `cached_in` on Q3, a `session_uid` + session name (or an honest `""`), and on
   graphify-ON cells a real row in `savings/graphify/`.
7. **Nothing else moved** — the real `~/.cage` untouched; writes only under
   `captures/<run-id>/`.
8. **Config provenance is recorded** (new, §2.7) — the manifest names which
   config file the run used (`cage.toml`, or `policy.toml` via fallback) and
   flags a coexisting legacy file. A capture whose numbers silently depend on an
   unnoticed legacy config is a trap; `cage doctor` reports this, so the driver
   just records it.

**Phase 1 output — one report per run** (`findings/runs/<run-id>/REPORT.md`,
[report-per-run.plan.md](report-per-run.plan.md)): the cells × checks grid, each
cell's numbers side by side (log · ledger · recount), and the **"what we learned"**
list — every field that did *not* appear where expected. That list is the actual
product of this phase; it pre-populates the field matrix (§6) and tells us which of
§3's 18 questions are even meaningful per surface.

> **Reporting shape (updated 2026-07-28):** publishing is now **one immutable report
> per run**, not one growing `VALIDATION-REPORT.md`. A run report holds only *that*
> run's data (no before/after columns, no forward references); each defect's status
> lives in its own dated finding doc; cross-run movement lives in
> `findings/HISTORY.md`. `publish_report.py` is structurally incapable of appending
> to a published report. The old layered `VALIDATION-REPORT.md` is retained SUPERSEDED,
> split into run-002 (pre-fix) + run-003 (post-fix).

**Three things Phase 1 must answer explicitly** (all unknowns today):

- **Where does Kiro CLI record usage, and does cage see it at all?** See §2.6 —
  this is now the single biggest suspected gap in cage's capture.

- **Does the graphify interceptor fire under the VS Code extensions at all?**
  The shim is a PATH interception; an extension that never shells out won't hit
  it. If it doesn't fire, the graphify A/B is CLI-only and the plan says so
  rather than pretending otherwise.
- **Are the Claude CLI and Claude VS Code stores distinguishable?** V1 vs V6 on
  the same questions is the cleanest possible test of cage's `surface=""` blank.

**Gate:** Arpit reviews `VALIDATION-REPORT.md`. A red cell is fixed (protocol
bug) or filed (cage finding) before Phase 2 — never papered over.

## 2.6 Kiro CLI — a real surface cage may not capture at all (2026-07-25)

**Correction to an assumption baked into cage and into this plan's earlier
draft: Kiro is not IDE-only. `kiro-cli` is a first-class CLI** (evolved from the
Amazon Q Developer CLI; `brew install kiro`). Verified against
[the Kiro CLI docs](https://kiro.dev/docs/cli/reference/cli-commands/):

- `kiro-cli chat --no-interactive "<question>"` — prints the first response and
  exits. **Ideal for scripted driving**, better than the IDE-only assumption.
- **Sessions are real and per-directory:** auto-saved every turn, UUID session
  ids, `--list-sessions`, `--resume-id <ID>`, `--delete-session <ID>`.
- `--effort low|medium|high|xhigh|max` — a real effort-tier axis (this is what
  Q17 exercises, and it feeds cage's effort-suffix family pricing).
- **Storage:** `KIRO_HOME` (default `~/.kiro`) holds "global agents, prompts,
  skills, steering, settings, **and sessions**". Separate debug logs live in
  `$TMPDIR/kiro-log/` (macOS) — those are diagnostics, not usage.

**Why this is a probable cage gap** — three suspicions. **Two are now
addressable by configuration alone** (v0.36, 2026-07-27 — see §2.7); the third
is what Phase 1 must actually discover:

1. **Unknown source** — `paths.agent_log_sources()` knows exactly one Kiro
   location: the IDE's `kiro.kiroagent/dev_data/tokens_generated.jsonl`. Nothing
   points at `~/.kiro`'s session store. **Fixable by config** once the path is
   known (`[sources.kiro] paths = […]`) — but the path is still unknown.
2. **Mislabelled surface** — `transcript.parse_kiro_calls` hardcodes
   `surface="ide"`. **FIXED as of v0.36:** a source can now declare
   `surface = "cli"` and `importcmd` restamps the row, so a non-IDE Kiro store no
   longer inherits `ide`. Phase 1 confirms it end to end on real data.
3. **Format — the open one.** If Kiro CLI's session store is a different shape
   from the flat `tokens_generated.jsonl`, no config fixes it: `[sources]`
   reuses an existing parser (`format = "claude|copilot|kiro"`), so a new shape
   needs a **fourth parser**. Phase 1's discovery decides whether this is a
   config-only win or a code change.
   *Upside if it's a new shape:* the IDE token log is cage's thinnest input (no
   timestamps, no session boundary, model `"agent"`, output often 0), while the
   CLI store has **UUID session ids and per-turn saves** — a parser for it could
   fix three of Kiro's four weaknesses at once.

**Phase 1 tasks for this cell (V5/V5b), in order:**

1. `kiro-cli --version`, `kiro-cli whoami` — confirm installed + authenticated.
2. **Snapshot before/after** a `kiro-cli chat --no-interactive` run across
   `~/.kiro/**`, the IDE globalStorage path, and `$TMPDIR/kiro-log/` — find
   *every* file the run touches. This is discovery, not verification.
3. Inspect whatever it wrote: does it carry token counts? session id? model?
   timestamps? Record the shape verbatim in the validation report.
4. Run `cage import --agent kiro` and check whether cage sees any of it.
5. **Try the config fix immediately** (this is the payoff of §2.7): add to the
   run's `cage.toml`

   ```toml
   [sources.kiro]
   paths   = ["<the path discovered in step 2>"]
   surface = "cli"          # NEW in v0.36 — without this the row would read "ide"
   ```

   then re-import and check `cage doctor --paths` (which now prints
   `surface=<declared|parser>` per source). **If rows appear with
   `surface="cli"` and correct tokens, the whole gap was configuration** — record
   the working stanza in the report as the fix.
6. **If the rows do NOT parse** (empty, or wrong numbers), that is the
   fourth-parser finding: capture the shape verbatim and file it. Do **not**
   write a parser inside the golden-set task.

Until step 2 is done, **the plan does not claim to know where Kiro CLI logs** —
that discovery is the point of the cell.

## 2.6a Standing exception to verbatim capture — Kiro CLI (2026-07-28)

Kiro CLI stores everything in one SQLite DB
(`~/Library/Application Support/kiro-cli/data.sqlite3`) that **co-locates an
`auth_kv` credentials table and every directory's full conversation text** with
the usage metadata. It therefore **cannot be copied verbatim** into a shareable
corpus — the one place the byte-exact rule (§2.1) cannot hold.

The recorded exception: capture a **redacted, workspace-scoped projection**
(conversation_id, timestamps, model, the token schema, credits, and per-turn
*character lengths* only — leak-tested for class names, code and auth), and mark
check 2 as `◻ n/a` rather than passing it. Forced by the store's shape, not a
shortcut; applies to Kiro CLI alone — every other surface stays byte-exact.

A future cage SQLite parser inherits the same constraint: read counts, ids and
times, **never the `value` transcript body**. Counts-never-content is harder here
than anywhere else in cage, because the content sits in the same row as the
metadata.

## 2.7 What v0.36 changed under this plan (2026-07-27)

Two cage changes landed while this plan was being written; both matter here.

- **`[sources]` gained a `surface` key.** `LogSource` now carries `surface`, and
  `importcmd` restamps an imported row's surface **only when a source declares
  one** (absent ⇒ parser-derived, byte-identical). Validated against
  `cli|vscode|ide|""` in both schema shapes; an invalid value becomes a
  `problems` entry, never a raise. `cage doctor --paths` shows
  `surface=<declared|parser>` per source, and `cage query sources` documents the
  key. **Effect on this plan:** the mislabel half of the Kiro gap is already
  fixed, and V5's step 5 can attempt a config-only resolution on the spot.
- **The config file is now `cage.toml`** (`policy.toml` still read as a
  fallback; `cage setup` migrates a lone legacy file; both present ⇒ `cage.toml`
  wins with a warning). **Effect on this plan:** every config stanza the golden
  set writes goes in `cage.toml`; the driver must not hard-code `policy.toml`,
  and manifests should record which config file each run used (a capture whose
  numbers depend on an unnoticed legacy file is a trap).

## 3. The question set (`questions/core.toml`)

Each entry: `id · prompt · dimension · pause_before · expect` (what capture
signal it should produce). Designed so **every field cage records has at least
one question that exercises it**, and several that should prove a field is
*absent* on a given surface.

| id | dimension exercised | prompt (verbatim, deterministic-ish) | what it should produce |
|---|---|---|---|
| Q1 | **floor / minimal call** | "Reply with exactly: ok" | smallest possible tokens_in/out; proves a row exists at all |
| Q2 | **large input → cache creation** | "Read `workspace/big_module.py` and summarize its public API in 5 bullets." | large tokens_in; `cache_creation_input_tokens` on claude ⇒ `cache_write_in` |
| Q3 | **cache read** (run immediately after Q2, same session) | "Now list the same file's imports." | `cache_read_input_tokens` ⇒ `cached_in` — the 98%-cache reality check |
| Q4 | **long output** | "Write a 400-word explanation of what this repo does." | high tokens_out; catches out-token loss (kiro logs 0) |
| Q5 | **tool use / edits** | "Add a docstring to `workspace/util.py`'s `slugify` function." | file-edit records; `scope`; provenance-relevant signals |
| Q6 | **multi-turn + human gap** (`pause_before = 90s`) | "What did you just change?" | a real `gap_ms` ≈ 90s → derived attention minutes |
| Q7 | **idle-cap overflow** (`pause_before = 15min`) | "Summarize our conversation so far." | `gap_ms` > the 10-min cap ⇒ proves capping, not raw summing |
| Q8 | **session naming** | "Let's call this session 'cage golden run'. Now: what is 2+2?" | claude `summary` record; VS Code `customTitle`/`generatedTitle` |
| Q9 | **untitled session** (new session, ask one throwaway question, exit) | "hi" | a session with **no** title ⇒ manifest `session_name = ""` |
| Q10 | **model switch** (where the CLI supports it mid-session) | "/model <other>" then "Reply with exactly: switched" | two `model` values in one session ⇒ pricing match per row |
| Q11 | **unpriced / router alias** (copilot) | ask anything on the default `copilot/auto` route | a row whose model matches no price row ⇒ **UNPRICED**, never $0 |
| Q12 | **premium request** (copilot) | one question on a premium model | `totalPremiumRequests` ⇒ `premium` field |
| Q13 | **refusal / short answer** | "What is my home address?" | a short, safe answer — proves refusals still meter |
| Q14 | **error / interrupt** | start a long generation, Ctrl-C mid-stream | partial/truncated record ⇒ the truncated-tail case, *genuinely* produced |
| Q15 | **parallel sessions** | two sessions started within a minute, one question each | distinct session ids ⇒ unique `session_uid`, per-session manifest rows |
| Q16 | **second project** | same as Q1 but from a different scratch repo | a different `project`/cwd basename ⇒ `cage report --project` |
| Q17 | **reasoning effort** (where offered) | same prompt at low and high effort | effort-suffixed model ids ⇒ family-match pricing, never `exact` |
| Q18 | **rapid burst** | five one-word questions back to back, no pauses | many rows, tiny gaps ⇒ attention stays near zero (no inflation) |

Notes:

- Prompts are fixed text so runs are comparable; answers will vary (LLMs), which
  is fine — **we assert on capture structure and token accounting, never on the
  model's words.**
- Q14's interrupt is how we obtain a *real* truncated file, replacing the
  manufactured edge case the lab plan now forbids.
- Q9 and Q11–Q12 exist mainly to prove **absence** honestly (no title; no price
  row; no premium on non-copilot).

## 4. Graphify pairing (`questions/graphify.toml`)

**Two runs per agent, identical questions, one variable.** That's what makes the
savings number attributable rather than asserted.

| run | setup | expectation |
|---|---|---|
| **A — without graphify** | graphify shim not on PATH; agent answers architecture questions by reading files | large `tokens_in`; **no** savings rows |
| **B — with graphify** | `cage setup` graphify interceptor wired; same questions | smaller `tokens_in`; a real saving in `savings/graphify/savings-<month>.jsonl` |

Questions (chosen because graphify's graph should genuinely beat raw file reads):

| id | prompt |
|---|---|
| G-Q1 | "How does the ledger writer relate to the import path in this repo?" |
| G-Q2 | "Which modules depend on `policy.py`, and what would break if it changed?" |
| G-Q3 | "Explain the data flow from capture to the report surface." |
| G-Q4 | "Where is pricing decided, end to end?" |

The pair yields the one number cage exists to produce, measured rather than
modeled: **A.tokens_in − B.tokens_in vs the receipt's claimed `saved`.** If those
two disagree materially, that is a finding of the highest possible value —
it means the savings claim doesn't survive an A/B.

Run both against the **same** frozen workspace so the only variable is graphify.

### 4.1 CORRECTION (Phase 1, 2026-07-28) — the agents don't invoke graphify

**The A/B as designed above did not fire.** In V2/V4 (graphify ON) both
`claude -p` and `copilot -p` answered the architecture question **without ever
shelling out to graphify**, so the PATH interceptor never ran and **zero** savings
rows were produced. The savings path itself is fine — invoked directly,
`cage data graphify -- graphify explain …` filed a correct row
(`raw_alternative=11,810 · actual=118 · saved=11,692`, `modeled`, 0.6).

This is not just a protocol bug to route around; **it is a product-level
finding** (see the report's §3.3, and compare the 2026-07-22 capture report's
"0 real receipts across 36,451 calls"). If agents don't reach for graphify
unprompted, then in real use a graphify saving exists **only when a human runs
the wrapper deliberately** — which is a plausible explanation for cage's empty
receipt ledger in the wild, and a question about the tool's adoption path, not
its accounting.

Phase 2 must therefore measure the A/B **honestly rather than hopefully**, and
say which of these it did:

| mode | what it measures | honesty |
|---|---|---|
| **agent-prompted** — the question explicitly instructs the agent to use graphify | the saving *when the tool is actually used* | measured, but the trigger is artificial — must be labelled |
| **driver-invoked** — the driver runs graphify itself and compares against the A-run's file-reading tokens | the saving the tool *can* deliver | measured A−B; the counterfactual is explicit |
| **unprompted (observed)** | whether agents reach for it on their own | the finding above — **record the zero**, don't retry until it passes |

The unprompted result is data, not a failure: keep running it and keep reporting
the zero.

## 5. Manual VS Code / IDE checklist (`manual/vscode-checklist.md`)

Extensions can't be driven headlessly, so this is a human script for Arpit. Each
step says what to do, then what to record. The driver's snapshot/copy step is
exposed as `python golden/drive.py --manual-capture --agent copilot --surface vscode`,
run **before** and **after** the manual session so capture stays mechanical.

**Copilot Chat (VS Code)**

1. Pre-capture: run `--manual-capture ... --phase pre`.
2. New chat in the golden workspace. Ask **Q1** ("Reply with exactly: ok").
3. Ask **Q2** then **Q3** (large file, then the follow-up) — cache behavior.
4. **Rename the chat** to `cage golden run` → this is the `customTitle` path.
5. Open a **second** new chat, ask "hi", leave it unnamed → the
   `generatedTitle`/no-title path (Q9).
6. Ask **Q12** on a premium model if your plan has one.
7. Wait ~15 minutes, ask **Q7** → real over-cap gap.
8. Post-capture: `--phase post`. Record in `_template.md`: chat titles, model
   picker values, approximate times, anything the UI showed about premium usage.

**Kiro (IDE)**

1. Pre-capture.
2. In the golden workspace, ask **Q1**, **Q4** (long output), **Q5** (an edit).

## 6. The deliverable: `findings/field-matrix.md`

The point of all this. One table, generated from the captures — for every
(agent × surface), for every field cage records:

```
field            claude/cli  claude/vscode  copilot/cli  copilot/vscode  kiro/ide
tokens_in        ✅ exact    ✅ exact       ✅ exact     ✅ exact        ✅ prompt only
tokens_out       ✅          ✅             ✅           ✅              ❌ always 0
cached_in        ✅          ✅             ✅           ❌ absent        ❌
cache_write_in   ✅          ✅             ❌           ❌              ❌
model            ✅ exact    ✅ exact       ✅ exact     ⚠ router alias  ❌ "agent"
timestamp        ✅ per turn ✅ per turn    ⚠ shutdown   ✅ per request  ❌ import-time
session id       ✅          ✅             ✅           ✅              ❌ constant
session title    ⚠ summary   ⚠ summary      ❌           ✅ customTitle  ❌
gap_ms           ✅          ✅             ❌           ❌              ❌
premium          ❌          ❌             ✅           ⚠ ?             ❌
surface marker   ❓ TBD      ❓ TBD          ✅ store     ✅ store        n/a
```

Plus two rows that record *how* a value was obtained, not just whether it exists
(both matter after v0.36 — §2.7):

```
surface source   parser-derived | DECLARED via [sources.<x>] surface = …
config file      cage.toml | policy.toml (fallback)   ← per capture run
```

Every cell must be **evidence-backed**: a link to the capture + the exact log
line (or the proven absence across N sessions). Cells marked `❓` are what the
golden run is for. The matrix drives three outputs:

- **cage capability decisions** — what can be built honestly, per surface.
- **honest-blank confirmations** — e.g. claude `surface=""` either gets confirmed
  as structurally impossible or gets fixed.
- **the lab's coverage map** — which M/G scenarios have real inputs, and which
  must report `NO REAL DATA`.

## 7. How this feeds the lab

- `golden/captures/<run-id>/logs/**` become the **primary inputs** in
  `inputs.toml` ([cage-lab-plan.md](cage-lab-plan.md) §2.1) — read in place,
  uncopied, sha-verified. The `samples/**` set stays as a secondary/legacy input.
- The graphify A/B pair (§4) upgrades the G-scenarios from "a saving was
  recorded" to "the saving matches a measured A−B difference".
- Q14 supplies the real truncated file; Q9 the real untitled session; Q15 the
  real parallel-session case — each replacing a case the lab currently has to
  report `NOT COVERED`.
- `transcript-map.json` lets the eyeball report cite **question id → log line →
  ledger row**, which is the cleanest possible manual check: *"I asked Q2, the
  log says 41,802 input tokens on line 7, cage recorded 41,802."*

## 8. Build order

**Phase 1 — setup + validation (gating, §2.5)**

1. `golden/` scaffold; `drive.py` snapshot/copy/manifest machinery + `--list`
   (no agent calls yet); frozen `golden/workspace/` committed.
2. **Graphify interceptor wired and verified live** in the workspace
   (`cage setup` + `cage doctor` interceptor check — presence is not liveness).
3. `questions/core.toml` — at minimum Q1/Q2/Q3 + one §4 architecture question.
4. **Scripted validation cells V1–V5** (claude CLI ±graphify, copilot CLI
   ±graphify, kiro CLI → expected `NOT AVAILABLE`).
5. `manual/vscode-checklist.md` + `_template.md` + `--manual-capture` ready, then
   **manual validation cells V6–V11** (Arpit: claude VS Code, copilot VS Code,
   kiro IDE — each ±graphify).
6. `findings/VALIDATION-REPORT.md` — 11 cells × 7 checks, three-way numbers, the
   "what we learned" list, and explicit answers on graphify-under-extensions and
   CLI-vs-VS-Code store distinguishability. **Arpit reviews. Red blocks Phase 2.**

**Phase 2 — scripted CLI sweep** (after sign-off)

7. Full 18-question core set on every available agent CLI + the graphify A/B
   pairs (§4).

**Phase 3 — manual VS Code / IDE sweep**

8. Arpit runs the extension surfaces per `manual/vscode-checklist.md`, capture
   bracketed by `--manual-capture --phase pre|post`.

**Phase 4 — payoff**

9. `findings/field-matrix.md` completed + reviewed.
10. Wire the captures into the lab's `inputs.toml`; re-point the M/G matrix
    ([cage-lab-plan.md](cage-lab-plan.md) §2.1/§3).
