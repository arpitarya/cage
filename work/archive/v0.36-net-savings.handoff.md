# Handoff — cost of use vs the tool's own cost

**The bug in one line:** `roi`/`verdict` know what a tool *spends on itself*
(`receipt.meta.tool_cost_usd`) but not what it *costs to use*. graphify is AST-only and
declares **$0**, so `cage insights verdict graphify` computes `net = gross − 0` and
reports **SAVING** — on the very sessions leg D measured costing ~14% more
([finding](regression/2026-08-01-finding-saved-is-gross.md)).

**Two deliverables:**

- **NET-2** — stop `verdict` over-claiming. Small, and it stops cage actively misleading.
- **NET-3** — task-level `net saved`. Medium, and it gives the number a real meaning.

**Not in scope:** the A/B answer. `cage insights compare` already does that; it only
lacks data (`MIN_COMPARE_N = 5`, leg D produced 1). That's a lab task, not a build.

---

## The distinction the data model is missing

| | what it is | where it lives today |
|---|---|---|
| **tool's own cost** | what the tool itself spends (graphify: $0) | `receipt.meta.tool_cost_usd` → `roi` |
| **cost of use** | the turn that invoked it · the hook's injected context · a re-read after a thin answer | **nowhere** |

`verdict`'s rule is `net = roi saved − roi own-cost`. With own-cost self-declared as
`$0`, net collapses to gross and the verdict is structurally optimistic for exactly the
class of tool cage exists to evaluate: cheap, deterministic, context-injecting.

## Hard constraint — graphify receipts are call-less

They carry a `task` but **no `call`** (that is why `receiptprice`'s ladder exists at
all). So:

- **Per-query net is impossible** for shim-pushed receipts. Do not fake a link.
- **Transcript-detected** use *can* be linked — the parser sees the tool-use block and
  the turn's usage in the same record.
- **Task-level net works for both**, via the existing `taskgroup` join.

Build task-level. If per-query is ever wanted, it needs the transcript route to stamp
`call` at capture time — a separate change, not this one.

---

## NET-2 — `verdict` must not call a $0-self-declared tool a SAVING

Today: `own_cost == 0` ⇒ `net == gross` ⇒ `SAVING`, at full confidence.

Required behaviour: when a tool's own cost is **absent or zero** and **no cost-of-use
figure is available**, `verdict` must not assert SAVING. Options — pick one and say why:

- a distinct verdict (e.g. `SAVING (GROSS)`) that names what is excluded, or
- `INSUFFICIENT DATA` for the net line, with gross still shown and labelled

Either way the output must state that the cost of *using* the tool is not in the number,
and point at `cage insights compare` as the measured alternative. `verdict` is a **pure
composer** — it computes no new statistics. Preserve that: this is a refusal rule, not
a new calculation.

## NET-3 — task-level net saved

`net = gross − (measured token cost of the task's turns attributable to tool use)`.

- Join via `taskgroup` (task-id first, session-window fallback) — already built.
- Gross is `modeled`; the subtrahend is `measured`; **the result is `modeled`** and
  carries its **own** confidence, lower than gross. Never let net read as measured.
- Report gross **and** net side by side. Replacing gross would destroy the comparison
  and hide what changed.
- Where the attributable cost can't be determined, print net as unavailable — never
  silently equal to gross.

**Open question for the executor:** what counts as "attributable"? The whole task, only
turns containing a tool-use block, or turns within a window of the receipt `ts`? Each is
defensible and each gives a different number. Decide, document it in `FORMULAS.md`, and
make the choice visible in `cage query`.
