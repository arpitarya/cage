# Proposal — timestamps get ONE normal form (UTC), compared only after normalization

> **ARCHIVED — IMPLEMENTED for v0.45.0 (unreleased), 2026-08-02.** Living spec:
> [FORMULAS §2.14](../../docs/FORMULAS.md) · [GLOSSARY](../../docs/GLOSSARY.md) *UTC normal form* ·
> `cage query agent-authorship` · [commitjoin.py](../../cage/commitjoin.py).
> Evidence: [finding](../regression/2026-08-02-finding-commit-window-timestamp-skew.md).
> Built from [handoff](v0.45-rev-ts.handoff.md) + [prompt](v0.45-rev-ts.prompt.md).
>
> **This proposal is history, and the build corrected it three times:**
> (1) the `…THH:MM:SS[.mmm]Z` sketch below renders *optional* milliseconds, which is
> still not totally ordered — the shipped form is fixed-precision **seconds**;
> (2) **failure shape 2 below is FALSIFIED** — git renders `%cI` as `…Z` at zero
> offset, never `+00:00`, so pure-UTC repos were correct all along, and that is
> precisely why milliseconds would have been a *regression*
> ([finding](../regression/2026-08-02-finding-commit-window-timestamp-skew.md));
> (3) *"not rewritten"* understates the frozen-row consequence — a corrected sweep can
> *add* rows on corrected shas beside the wrong ones, so the `_authorship` cursor is
> deliberately **not** invalidated. Where this disagrees with the living spec, the
> spec wins.

**The v0.43 authorship joins are wrong on any non-UTC machine — including the
maintainer's (IST).** `commitjoin.commit_windows` reads `git log --format=%h|%cI`
(committer-**local** offset, e.g. `+05:30`) and `window_for` compares those strings
**lexicographically** against UTC `...Z` transcript/call timestamps. String order
across different offset representations is meaningless.

## The three failure shapes (all live at HEAD)

- **Offset skew:** on IST, a 09:00-IST commit renders `...T09:00:00+05:30` (= 03:30Z);
  an edit at `05:00Z` (10:30 IST, *after* the commit) string-compares below it and
  buckets into the earlier window. Every edit and window-joined call shifts by the
  offset — agent-vs-human attribution lands on the wrong sha.
- **Same-second boundary:** even pure-UTC repos fail the documented inclusive bound —
  `"…T10:00:00.000Z" <= "…T10:00:00+00:00"` is False (`.` sorts above `+`). The
  existing test passes only because it compares byte-identical `+00:00` strings.
- **Mixed-offset sort:** local commits + GitHub-web/CI `+00:00` merges mis-sort
  `pairs.sort`, producing windows out of chronological order.

## Where

`commitjoin.py:89` (window build), `:99` (sort), `:118` (`window_for`), `:291` ·
`authorcapture.py:107` (coverage cursor) · every consumer that hands a raw transcript
ts into a window compare. `commitview._iso` (~:62) already does the right thing for
`--since` — the fix is promoting that, not inventing anything.

## Sketch

- One helper (promote `_iso`'s `fromisoformat` → UTC into a small shared home;
  `commitjoin` is the natural owner — it defines `Window`).
- Normalize **at window build** so `Window.lo/hi` are always UTC-`Z` strings of one
  shape; normalize the probe ts in `window_for`/`newest_ts`. String compare stays
  (determinism law — no datetime objects in stored rows), but only ever between
  normalized strings.
- Guard: extend `goldenseed` (which already pins committer dates) with a **non-UTC
  offset fixture** (`+05:30`) and a same-second-boundary case; assert the join lands
  on the right sha. The current suite is green *because* it never leaves UTC.
- Re-derivation: windows are computed at read time, so historical joins self-heal on
  the next sweep — except rows already **recorded** by `originrecord` (frozen by
  idempotency key). State that plainly in the changelog: pre-fix provenance rows on
  non-UTC machines are suspect; the append-only log is not rewritten.
