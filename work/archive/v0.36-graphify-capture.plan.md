# Graphify capture — see every use, model every saving

**Plan of record** for making graphify usage fully visible to cage (tokens, usage,
freshness) and for modeling *prospective* graphify savings honestly. Grounded in
the G0.5 finding that graphify's PreToolUse hook invokes nothing (static context
injection), so **every existing capture route is invocation-gated while real usage
may not involve an invocation at all**.

Sequenced **before G1** — the transcript route answers G1's "did cage see it" arm
for free.

## 1. The gap (evidence, 2026-07-28)

- G0.5 proved the hook is a **static bash conditional** — no subprocess, nothing
  for the PATH shim to intercept. The PATH-bypass hypothesis is dead.
- Therefore all three existing routes (PATH shim · graphify's native receipt shim
  ≥0.5.0 · the hook) capture **only explicit invocations** — and miss:
  - absolute-path / venv entry-point invocations (no PATH traversal),
  - **the invocation-less saving**: the agent reads `GRAPH_REPORT.md` (21KB)
    *instead of* scanning N source files — a real saving, no process spawned,
  - VS Code surfaces (hooks never fire there anyway),
  - a parse-miss today files **nothing** — right for savings (never fabricate),
    wrong for observability: usage becomes invisible.
- Ruled out by inspection: watching `graphify-out/cache/` (entries are AST
  nodes/edges + `raw_calls` — zero usage signal) and any watcher-shaped capture
  (banned by design, ADR 0002 spirit).
- `graphify update .` is AST-only, $0 — nothing to meter. **VERIFY against
  graphify's source** that no verb (wiki, edge inference) calls an LLM; if one
  ever does, the existing proxy is the route, never a new mechanism.

## 2. GC1 — usage rows (never invisible)

- One row per wrapped/native/transcript-detected graphify run:
  `{op, args_hash, exit, ms, outcome: receipt|unmeasurable|empty}`.
- **Diagnostic, never priced, never in derived money views.** Read by
  `cage doctor` (and `CAGE_DEBUG` traces), not by report/attrib.
- Home: `state/` (state files are never read by derived views — the cleanup
  invariant already guarantees a usage row can't change a reported number).
- The payoff sentence doctor can finally print: *"graphify ran 47×, 3 receipts,
  44 unmeasurable"* vs *"graphify never ran"* — the distinction the
  0-real-receipts mystery lacked for nine days.

## 3. GC2 — transcript-side detection (the architectural fit)

### 3.0 GC0 verdict — do the logs carry tool command + result? (probed 2026-07-28)

Probed the **real** on-disk logs on this machine (24 copilot CLI sessions, 145
copilot VS Code chat-session files, the kiro token log), not only the sanitized
fixtures. Verdict per agent × surface:

| Agent · surface | Carries tool **command**? | Carries tool **result** text? | Verdict |
|---|---|---|---|
| **claude** (cli + vscode) | **yes** — `tool_use` block, `name:"Bash"`, `input.command` | **yes** — the following `tool_result` block's text | **SHIP now** (GC2 builds it) |
| **copilot cli** (`session-state/*/events.jsonl`) | **yes** — `tool.execution_start`, `toolName:"bash"`, `arguments.command` | **yes** — `tool.execution_complete`, `result.content`/`result.detailedContent` | **detectable — OUT OF SCOPE**; finding filed, a follow-up builds it |
| **copilot vscode** (`chatSessions/*.jsonl`) | **partial** — `response[]` tool-call blocks carry `toolId`/`invocationMessage`/`toolSpecificData`; the full shell command string is not cleanly isolated | unverified — result text fidelity not confirmed | **OUT OF SCOPE**; needs a fidelity probe before any build |
| **kiro** (cli + vscode) | **no** | **no** | **HONEST-LIMIT** — recorded, never approximated |

- **claude** is the only surface GC2 implements now. Its `tool_use`/`tool_result`
  shape is already verified (cage's own `transcript.parse_provenance` reads
  `tool_use` blocks), so the counterfactual has real command + result to work on.
- **copilot cli** *does* carry everything needed (command + result text) — this is
  a **positive finding**, but per handoff §3 the copilot/kiro *implementation* is
  out of scope; a follow-up can build copilot-cli detection off this note. It is
  recorded here so the negative-space is a deliberate, dated choice, not an
  oversight.
- **copilot vscode** records tool *invocations* but not (verifiably) the full
  command + result text — a fidelity probe must precede any build.
- **kiro** carries no tool bodies at all: its only log is
  `tokens_generated.jsonl` (`{model, provider, promptTokens, generatedTokens}`),
  and the Kiro-CLI SQLite store is counts-only by cage's own PII law (the closed
  whitelist in `transcript.py` forbids reading `history[].assistant`). So kiro is
  HONEST-LIMIT by *both* log shape and PII contract — the `gap_ms` precedent
  exactly. Never fabricated.

### 3.1 The two detections (claude)

- Pull-based, at `cage import` — the same trigger as everything else (ADR 0002).
- Two detections in the transcripts cage already parses:
  1. **Bash tool calls** whose command matches `graphify (query|path|explain)` —
     catches every invocation form on every surface. The tool **result text is in
     the transcript**, so `graphifymeter`'s counterfactual parser
     (`_SRC_QUERY`/`_SRC_EXPLAIN` → cited files → `raw_alternative`) is reused
     nearly verbatim. `method="modeled"`, existing confidence constant.
  2. **Read tool calls** on `graphify-out/GRAPH_REPORT.md` / `wiki/**` — the
     report-read saving. Counterfactual: the graph's own source-file corpus (see
     GC5b) — weaker, so **lower confidence, still `modeled`**, and footnoted as
     `report-read` so it's never conflated with a query receipt.
- **GC0 gates the fan-out** (verdict in §3.0, probed 2026-07-28): claude ships;
  copilot cli is detectable but out of scope (finding filed); copilot vscode
  needs a fidelity probe; kiro is HONEST-LIMIT. The `gap_ms` precedent exactly.
- File reads for the counterfactual happen at import time, when files may have
  drifted from the moment of the query — acceptable within `modeled`, noted in
  FORMULAS.md.

## 4. GC3 — dedupe (the one real design problem)

- Wrapper ↔ native already handshake (`CAGE_GRAPHIFY_METERED=1` + ledger
  snapshot).
- Transcript receipts get **deterministic ids** — hash of
  `(session, op, args_hash, answer_hash)` — so re-imports dedupe in the standard
  path and `union_by_id` collapses transcript-vs-shim duplicates of the same
  query. Tree/first-writer wins per existing merge law.
- Report-read receipts are per `(session, file, mtime-bucket)` — one per read,
  not per line.
- Test: run one query through shim + transcript import → exactly one receipt.

## 5. GC5 — modeling what graphify is *going to* save

Three claims, three tags, never blended:

- **(a) Per-query expected saving** — the `insights estimate` pattern applied to
  graphify receipts: median+IQR from exact-key history (repo/scope).
  `modeled`; **refuses below `MIN_ESTIMATE_N`**; scored later by
  `insights calibration` — the measured hit-rate is the only confidence source,
  the estimator never self-reports. Needs GC2 history to exist.
- **(b) Repo ceiling, day-one** — from the graph itself, no history, no LLM,
  deterministic: the graph maps communities/god-nodes → source files, so cage can
  compute *"an architecture question here avoids ~N files ≈ X tokens vs a
  ~Y-token answer"*. A static bound, `modeled`, printed as a band with its
  derivation footnoted. This is the "is graphify worth installing in this repo"
  number, available before a single query has run.
- **(c) Break-even** — no new math: `insights verdict graphify` already composes
  attrib/roi/trend + break-even; (a)/(b) feed it. Verdict stays a pure composer
  and keeps its INSUFFICIENT-DATA refusal.
- **Law:** a projection is a band, labelled, refusable — never summed into a
  measured total, never printed without its method tag.

## 6. What must not change

- Fail-open write paths; determinism of derived views; counts-never-content.
- A parse miss still files **no receipt** (usage row instead — GC1).
- The golden fixtures pin rendered output; new columns/footnotes re-bless
  goldens, never fork render logic.
- No watcher, no scheduler, no graphify-side changes required (native-shim
  cooperation stays optional).
