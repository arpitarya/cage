# One report per run — split the layered validation report

**Plan of record** for restructuring cage-lab's validation reporting: **every run
produces its own self-contained report**, and no report ever accumulates a later
run's results.

## 1. The problem this fixes

The current `VALIDATION-REPORT.md` layers three things in one file:

1. the **post-fix re-run** (prepended, current),
2. the **pre-fix baseline** (§1/§2, superseded but preserved),
3. **findings** whose lifecycle spans both (§3.1 fixed, §4.5 resolved, §4 open).

Result: line 92 reads `227,298 · 189,788 ❌` while line 14 reads `8/8 exactly
227,298`. Both are true — of different runs — but a reader landing mid-file
cannot tell which world they're in. Banners helped; they didn't fix the shape.

**The root cause is that one document is answering three different questions.**
Split the questions, and each answer becomes unambiguous.

## 2. The split

| artifact | answers | lifetime |
|---|---|---|
| **Run report** — `findings/runs/<run-id>/REPORT.md` | "What happened in *this* run?" | **Immutable** once published. Contains only that run's cells, numbers, checks. No before/after columns, no forward references |
| **Finding doc** — `work/regression/<date>-<slug>.md` | "What is this defect, and what is its status *now*?" | **Mutable status, append-only history**: `OPEN → RESOLVED (fixed <date>, evidence)`. Links the runs that observed it |
| **History index** — `findings/HISTORY.md` | "What runs exist, and how did the numbers move?" | Append-only, one row per run |

The rule that follows: **a run report never mentions a later run.** If you want
to know whether a run's numbers are still current, the history index tells you —
not a banner inside the report.

## 3. What a run report contains

Self-contained by construction:

- run id, timestamp, machine, cage version, agent versions, **config file in use**
- the cells executed in *this* run, with their checks
- the numbers *this* run produced (log · cage · lab recount), each reconciled
- findings **observed** in this run — one line each + a link to the finding doc
  (never the finding's full lifecycle, which lives in the finding doc)
- what was *not* covered, and why
- its own sha256 (existing `publish_report.py` mechanism, unchanged)

Explicitly **not** in a run report: "before/after" comparisons, superseded
banners, or the status of a finding as of a later date.

## 4. Cross-run comparison, done properly

The comparison that currently lives inside the report moves to
`findings/HISTORY.md`, generated from the run reports:

```
| run | date | phase | cells | copilot tokens_in | kiro | verdict |
|-----|------|-------|-------|-------------------|------|---------|
| 003 | 07-28 pm | P1 re-run | V1–V5b | 227,298 / 233,675 ✅ | 12/15 credit rows | all green |
| 002 | 07-28 am | Phase 1  | V1–V5b | 189,788 / 191,414 ❌ | 0 rows ❌ | 2 findings |
```

That table shows the movement **explicitly**, which is what the layered report was
trying to do implicitly — and it can't be misread, because each row names its run.

## 5. Retro-split of the existing report

The current layered file becomes two self-contained reports:

- **run-002 (pre-fix, 2026-07-28 am)** — the original interim: V1/V2 green,
  V3/V4 check-5 red at 189,788/191,414, V5/V5b red. Findings observed: copilot
  undercount, shim recursion, graphify A/B, kiro SQLite.
- **run-003 (post-fix, 2026-07-28 pm)** — the re-run: copilot exactly
  227,298/233,675, kiro 12/15 credit rows, claude byte-identical, self-heal proof.

Both published (append-only, hashed). The existing layered file stays in
`work/regression/` marked **SUPERSEDED — split into run-002 + run-003** — we
don't delete published evidence; we stop adding to it.

## 6. Acceptance

- Any run report, opened at a random line, is unambiguous about which run it
  describes — **no banner required to avoid a misread**
- No run report contains another run's numbers
- `HISTORY.md` shows the pre-fix → post-fix movement in one table
- Every finding's *current* status is answerable from its finding doc alone
- All reports hashed; hashes recomputed and verified
- `latest-validation-report.md` points at the newest run report

## 6.1 Open questions

- **Run-id scheme:** `runs/<YYYYMMDD-HHMM>-<phase>/` (matches the existing
  capture run-ids) or a monotonic `run-003`? Default: **match the capture
  run-id**, so a report and its captures share a name.
- **Does the manual sweep (V6–V11) get its own run report?** Default: **yes** —
  it is a distinct run with distinct cells, and merging it into a scripted
  report would recreate exactly the layering problem this plan removes.

## 7. Legacy reports — the same split, applied backwards (phase 7)

The golden-set validation reports are done. The **pre-golden-set** reports carry
the identical defect and were never touched.

### 7.1 What's still layered

**`2026-07-22-capture-report.md`** — the real-ledger lab run. It mixes all three
questions in one file:

- **the run's observations** (per-agent table, 36,451 calls, cache split);
- **eight findings inline** (F1–F8), *with lifecycle baked into headings* —
  `F3 … ✅ RESOLVED v0.34.0`, `F5 … ✅ RESOLVED v0.34.0`, `F7 … ✅ RESOLVED
  v0.34.0 — reframed`. **A later status inside a run report is exactly what the
  new model forbids**: the 07-22 run did not observe those resolutions;
  a *later* release did.
- **corrections living outside it** — `2026-07-23-f2-correction.md` and
  `2026-07-24-f1-root-cause.md`, which exist *because* the report couldn't be
  edited. They are the layering problem turned inside out: a finding's history
  scattered across three files, none of which owns its status.

Also unsplit: `2026-07-25-cage-lab-baseline.md` (a run, no history row) and
`2026-07-24-{capture-log-hook-gap,field-gate-post-heal-check}.md` (findings
without finding docs).

### 7.2 The split to produce

| new artifact | content | source |
|---|---|---|
| **`2026-07-22-lab-run-001.md`** | *Only* what the 07-22 run observed: per-agent capture table, cache split, gap_ms coverage, the eight findings as **one line each + link**. **No resolution status.** | the report's observational sections |
| **`2026-07-22-finding-<slug>.md` × 8** | One per F1–F8, each owning its own `Status:` line and an append-only history | the F-sections + the two corrections + the "Follow-ups shipped" table |
| **`2026-07-25-lab-run-002-baseline.md`** *(or a HISTORY row if it is already self-contained — check first)* | the 07-25 baseline as a run | existing file |
| **HISTORY rows** | one per legacy run, same table as the golden runs | new |

**The two correction files are absorbed as *history entries* inside the finding
docs they correct — and remain on disk, cited.** They are published evidence;
they stop being the only place a correction lives.

### 7.3 The rules, unchanged from phases 1–6

- **Transcribe, never recompute.** Every number comes from the published text.
- **Nothing is deleted.** The 07-22 report and both corrections stay, marked
  **SUPERSEDED — split into lab-run-001 + 8 finding docs**.
- **A run report carries no later status.** `F3 ✅ RESOLVED v0.34.0` becomes:
  the run report says "F3 kiro capture empty — see finding doc"; the *finding
  doc* says `Status: RESOLVED (v0.34.0)`.
- Every number in the original appears in exactly one new artifact — none lost,
  none duplicated.

### 7.4 Why this is worth doing rather than leaving as history

Three reasons, in order of weight:

1. **`work/regression/` is what a future agent reads to learn what's broken.**
   Today F1's true root cause (a dead interceptor verb) lives in a *correction
   file*, while the original F1 text — "graphify is being run directly" — reads
   as current in the report. A finding whose wrong first diagnosis is more
   prominent than its right one is worse than no finding.
2. **The status is genuinely ambiguous today.** F1 says "0 real receipts"; the
   07-24 correction says that's false machine-wide; the golden-set later showed
   agents don't invoke graphify unprompted. Three partial answers, no owner.
   One finding doc resolves that.
3. **It makes the taxonomy usable.** The finding ids (`receipts-empty`,
   `health-contradiction`, …) were designed as stable handles across runs. They
   can only work if each id has a document.
