## G-SAV — `ts` never reaches the row

```python
def record(root=None, *, tool, raw_alternative, actual, op="", session="", task="",
           unit="tokens", method="modeled", confidence=1.0, source_files=0,
           import_id="", savings_id=None, **_ignore) -> str:
```

`schema.make_savings` **accepts `ts`**; `record()` does not, so a caller's `ts=` lands
in `**_ignore` and the row is stamped *now*. Every savings row therefore writes into the
**current** month's shard regardless of when the work happened.

**Fix:** add `ts: str | None = None` and forward it to `make_savings`.

**Keep `**_ignore`** — three real callers (`graphifytx` ×2, `graphifymeter`) pass through
a shim boundary, and this is a fail-open push path. Removing it is a separate decision.

**But name the hazard:** `**_ignore` is *why* a silently-dropped kwarg survived to
production. Consider a test asserting that every keyword `make_savings` accepts is also
accepted explicitly by `record()` — that makes the next such drop impossible rather than
merely unlikely. **Ask before adding it** if it turns out to constrain the shim contract.

## BUD-V-TEST — the tests borrowed a product table

Five `test_policysync` tests exercise **generic sync mechanics** — keep-customized,
update-stale-default, confirm-bucket, orphan-warning — and used `[budgets]` as their
worked example. The bundle now ships `[budgets]` commented out (opt-in, by decision), so
those mechanics can no longer be demonstrated through it.

**Why hand-writing `[budgets]` back into the fixture does NOT work.** The assertions
compare a project value against a **bundled** default (`bundled 25.0`, `1.0 → 2.0`).
With no bundled counterpart the classifier buckets an active `[budgets]` as
`project_own` and leaves it alone — which is exactly what BUD-V verified as *correct*
behaviour. The table must exist **in the bundle** for these tests to mean anything.

**So: re-point at a table the bundle actively ships.** The replacement must be:

1. present in `cage/data/cage.toml` as an **active** table,
2. **surviving `_strip_to_v016`** (which deletes `[meta]`, `[cleanup]`, and
   `import_before_export` — so `[cleanup]` is the *adds* example and cannot be this),
3. carrying a simple scalar key,
4. not already the subject of another test (`[tools] order` is taken).

Live tables: `[meta]` `[capture]` `[display]` `[cleanup]` `[debug]` `[tools]`
`[quality]`. **`[quality]` looks like the fit** — verify rather than assume.

### The real problem, and a decision to make

These tests couple **generic mechanics** to **whatever cage happens to ship**. That is
why removing one product table reddened five tests that have nothing to do with budgets,
and it will happen again on the next table removal.

The durable fix is a **synthetic bundle fixture** — the sync tests own a small fake
bundle and stop depending on product content entirely.

**Decide and state:** re-point now (cheap, green today, same fragility) · synthetic
fixture (more work, kills the class) · re-point now **and** file the synthetic fixture
as a follow-up. **The third is the recommendation** — but say which you did and why.
