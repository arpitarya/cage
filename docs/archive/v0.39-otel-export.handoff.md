# Handoff — `cage data export --otel`

**One-way export of the ledger as OpenTelemetry GenAI-conformant JSON.** Cage stays the
`$0` local ledger and *feeds* the enterprise stack (Langfuse, Helicone, any OTLP sink)
instead of competing with it.

---

## ⚠️ Review finding that changes the design: the spec is NOT stable

The proposal assumed OTel GenAI is a settled lingua franca. **It isn't.** As of the
v1.42.0 semconv release (June 2026) the `gen_ai.*` attributes moved to a **dedicated
repo and remain pre-stable** — no 1.0, pages labelled *Development*, and **names can
still change between versions**
([OTel blog](https://opentelemetry.io/blog/2026/genai-observability/) ·
[semconv status](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)).

That collides head-on with cage's determinism law — *same ledger + same policy ⇒ same
tables*. An export whose field names drift with an upstream spec would silently produce
different output from the same ledger.

**So the design gains a requirement the proposal didn't have:**

- **Pin and stamp the semconv version.** The emitted document carries the exact
  convention version cage targeted (e.g. `"semconv": "1.42.0"`), in **one constant**
  beside the other reviewable numbers (`constants.py`).
- **A spec bump is a deliberate, versioned change** — same discipline as
  `prices_version`: cage never silently follows upstream. Changing it is a changelog
  line.
- **Say "pre-stable" in the help text and the docs.** A user piping this into a vendor
  should know the shape can move. That is the honesty rule applied to an export format.

## Scope

**`cage data export --otel`**, alongside the existing `--csv` / `--study` / jsonl.

- Map **calls** → GenAI attributes: `gen_ai.system` (provider) · `gen_ai.request.model` ·
  `gen_ai.usage.input_tokens` / `output_tokens` · duration where `latency_ms` exists.
  Where cage has no honest value, **omit the attribute** — never emit a zero that reads
  as measured.
- **Receipts and savings have no GenAI equivalent.** Do not invent attributes for them.
  Either omit them entirely or carry them under a clearly cage-namespaced key
  (`cage.saved_tokens_gross`, …) — **decide and state which**. Inventing a `gen_ai.*`
  name that upstream doesn't define is the worst outcome here.
- **Method tags must survive.** A `modeled` number must not arrive at a vendor looking
  measured; carry `cage.method` on anything derived.
- Deterministic: stable key order, LF pinned, no clock, no randomness.
- **One-way REPORTING, exactly like CSV** — never an import source. The fleet bundle
  (`--study`) stays jsonl.

## What this is NOT

Not an OTLP exporter, not a network client, not an SDK dependency. Cage writes a file;
the user's collector ingests it. **stdlib only — `dependencies = []` is not negotiable**,
and pulling `opentelemetry-*` would end the `$0` guarantee.

## Can it run in parallel with CODEX-OUT and DEBT? **Yes — with two rules.**

Code collision is genuinely near-zero:

| item | touches |
|---|---|
| **CODEX-OUT** | `paths` · `wiringscan` · `doctorcmd` · `doctorbundle` · `agents` · `schema` · `ledger` · `report` · `proxy` · `runshim` · `policy` · `explain_data` + many tests |
| **DEBT** | `cli.py` · `CLAUDE.md` + one golden |
| **OTEL** | `exportcmd.py` · a new `otelout.py` · `constants.py` · `explain_data.py` + new tests |

**Only two real contact points:**

1. **`explain_data.py`** — CODEX-OUT deletes a codex mention from the stale-wiring
   entry; OTEL adds a new entry. Different regions of the same file: a trivial merge,
   but they will both touch it.
2. **The shared bookkeeping files** — `OPEN-WORK.md`, `WORKLOG.md`,
   `IMPLEMENTATION.md`, `CHANGELOG.md`, `DOC-REGISTRY.md`, and the **test-count line in
   README + CLAUDE.md**. Three agents each appending an entry and each editing the same
   count *will* conflict.

**The two rules for running them in parallel:**

- **Sequence the bookkeeping, not the code.** Each run does its own code + tests, then
  updates the shared docs **last**; whoever lands second re-reads and re-applies. The
  test count is the classic collision — whoever lands last owns the final number.
- **CODEX-OUT goes first if any two run truly concurrently.** It has by far the widest
  blast radius and re-blesses the most goldens; letting a smaller change land on top of
  it is much easier than the reverse.

**Recommended order if you'd rather not merge at all:** CODEX-OUT → OTEL → DEBT.
OTEL is the most isolated of the three and the safest to parallelise.

## Definition of done

- [ ] `cage data export --otel` emits GenAI-conformant JSON, deterministic byte-for-byte
- [ ] Semconv version pinned in `constants.py` and **stamped in the output**
- [ ] Help text and docs say the convention is **pre-stable**
- [ ] No `gen_ai.*` attribute invented; cage-only data is cage-namespaced or omitted
- [ ] Method tags survive; no fabricated zeros
- [ ] `dependencies = []` unchanged — stdlib only, no OTel SDK
- [ ] Never an import source; `--study` still jsonl
- [ ] `cage query` entry; `just test` green; goldens named
- [ ] Proposal archived per the lifecycle; IMPLEMENTATION / WORKLOG / DOC-REGISTRY /
      OPEN-WORK updated

## Out of scope

OTLP/network push · metrics vs spans modelling beyond a flat attribute map · re-import.
