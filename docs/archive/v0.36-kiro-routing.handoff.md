# Handoff — kiro capture routing (K2)

**The fix is two opposite changes to two different stores, and the hard part is neither
of them** — it's that `importcmd.run` is built on "one active sink per sweep", and the
IDE half deliberately breaks that.

**Why it matters:** kiro is paid. A per-project kiro cost has never been correct, and
credits are the billed unit. Decision + rationale: [ADR 0006](adr/0006-kiro-rows-are-machine-facts-not-project-facts.md).

---

## The two stores — opposite properties, opposite fixes

| | **IDE** | **CLI** |
|---|---|---|
| file | `dev_data/tokens_generated.jsonl` | `conversations_v2` (SQLite) |
| parser | `transcript.parse_kiro_calls` | `transcript.parse_kiro_cli_credits` |
| wired as | built-in adapter (`_ADAPTERS["kiro"]`) | **custom tool source**, `fmt="kiro-cli"` |
| carries | no project · `session="kiro"` · no `ts` | **keyed by cwd** · real conv id · real `updated_at` |
| row kind | calls | credits (`k_cred…`, own namespace) |
| **fix** | **route to the global ledger** | **scope by cwd + stamp `project`** |

Getting these backwards destroys attribution the CLI source genuinely supports.

---

## Change 1 — IDE rows route to the global ledger

**Rule:** kiro-IDE rows land in `paths.global_home()`, *unless* the ledger came from an
explicit override. `paths.active_ledger_source()` already returns exactly the three
tiers — `"override (--ledger/CAGE_BASE)"` · `"project (.cage/)"` · `"global (~/.cage)"`.

Put the decision in **one** resolver in `paths.py`, beside `canonical_ledger`. No caller
re-derives it.

### The real work: `importcmd.run` assumes one sink

Its own docstring: *"One active sink per run — never a double-write."* Everything below
is built per-root and is now wrong for the kiro leg:

| built per-root | what breaks |
|---|---|
| `seen = {c["id"] for c in ledger.calls(root)}` | kiro dedupes against the wrong ledger ⇒ re-appends every run |
| `_load_cursors(foot)` / `_save_cursors` | kiro's high-water mark stored against the wrong root |
| `_import_lock(foot, pol)` | the global write is unserialized ⇒ two projects importing at once can double-append |
| `_write_manifest(root, …)` | manifest FK points at a ledger that has no such rows |
| `_record_health` · `_record_capture_log` | project health claims kiro capture it doesn't hold |
| `_import_rollup(collected, …)` | the `captured N new` line counts rows that landed elsewhere |

**Approach: a contained nested leg, not a rewrite.** When the kiro sink differs from the
sweep's root, run kiro in its own small block against the global footprint — own `seen`,
own cursors, own lock, own manifest/health — and keep its counts separate in the
reported summary. Everything else in the sweep is untouched and must stay
byte-identical.

**Do not** hold both locks at once, and take them in a fixed order if ever nested — two
projects importing concurrently is the realistic deadlock.

---

## Change 2 — CLI credits scope by cwd

`_ingest_credits` calls `transcript.parse_kiro_cli_credits(f)` — default `workspace=""`,
which reads **every conversation on the machine**. That is the CLI double-count.

- Pass the project's cwd key when the sink is a project ledger.
- Stamp `project` on the credit row (`_kiro_cli_credit_row` sets none today).
- Global sink ⇒ no filter, as now.

**Verify the key format first.** `conversations_v2.key` is a cwd string; confirm how it
is normalized (trailing slash, symlinks, case) against a real store before filtering on
it — a near-miss silently yields zero rows, which looks exactly like "no kiro usage".

## Honesty on the read side

A project report now shows **no kiro**. Silence is indistinguishable from broken
capture — the failure cage exists to prevent. Say why:

- a `report`/`overview` footer line when kiro sources exist but route elsewhere
- `doctor`'s capture timeline names kiro's sink as global
- a `cage query` concept entry explaining the split

Overlaps **K3/K4** (the two unstated HONEST-LIMITs) — do the wording once, together.

## Migration — the past is not fixed

Existing project ledgers already hold duplicated kiro rows. **Append-only: they are
never rewritten.** This fixes the future only. Footnote it, and say so in the CHANGELOG
— a user who reads "kiro double-counting fixed" and then sees old numbers unchanged
will assume the fix failed.

## cage-lab impact

`03-verify.md` check 11 asserts `~/.cage` was untouched. After this, a **default** run
writes kiro there. Under the lab's explicit `--ledger` it still doesn't — which is
exactly why the override exception exists. Update the check to state both cases.

## Definition of done

- [ ] Kiro-IDE rows land in `~/.cage` when cwd is inside a project; **`--ledger`/`CAGE_BASE` still wins**
- [ ] Two project ledgers on one machine ⇒ the same kiro turn appears **once**, globally
- [ ] Re-import is still idempotent (0 new) against the *global* ledger
- [ ] claude/copilot capture **byte-identical** — assert it, don't assume it
- [ ] The `captured N new` summary never counts rows that landed in a different ledger
- [ ] CLI credits filtered by cwd; `project` stamped; key normalization verified on a real store
- [ ] A project report explains kiro's absence instead of showing nothing
- [ ] `just test` green; goldens re-blessed; CHANGELOG notes the behaviour change **and** that old rows stand
- [ ] ADR 0006 linked from the changelog entry; IMPLEMENTATION / WORKLOG / DOC-REGISTRY / OPEN-WORK updated

## Open questions for the executor

1. **Does the global leg run when capture is disabled for the project?**
   `policy.capture_enabled` is read from the *project* policy. Whose switch governs a
   write to the global ledger — the project's, the global one's, or both? Decide and
   state it; this is a real precedence question, not a detail.
2. **Does `cage import --ledger X` still capture kiro into X?** Per ADR, yes — explicit
   override wins. Confirm that is what the lab needs.
