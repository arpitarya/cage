## P2 — the Kiro proxy probe (the valuable one)

**Why this matters:** the store probe proved Kiro's token fields are null — even
with `--effort high`, even on a large input. One route was never tried. The
**proxy** puts cage *in the request path*, counting tokens itself instead of
reading Kiro's summary. This is the only remaining way Kiro becomes `measured`
rather than `estimated`.

1. **Find out whether `kiro-cli` honors a proxy / base-URL override** — env var,
   config file, `kiro-cli settings list --all`. Check; don't assume either way.
2. If it does: `cage data meter -- kiro-cli chat --no-interactive "<Q1>"`, plus
   one **large-input** turn, with cage in the path.
3. Record whether cage counted **real tokens**, and whether they reconcile
   against anything independent.

**Outcome A — it works.** Exact Kiro numbers exist. Document the proxy as the
recommended Kiro metering mode; the SQLite credits parser becomes the passive
fallback; Kiro may be tagged `measured` **on that path only** (credits stay
`estimated`). Answer the open question first: does a proxy-metered run also need
a `[sources]` entry, or does the proxy write receipts directly? Read the code
(`cage/metercmd.py`, `cage/proxy.py`) before writing guidance.

**Outcome B — it doesn't.** Record the *specific* reason (no override / cert
pinning / the CLI tunnels its own transport). Then *"Kiro CLI cost is
credit-derived and `estimated`, by vendor design"* becomes the **final,
documented** answer in the field matrix and `FORMULAS.md`.

**Both outcomes are results.** A negative closes the question permanently and
closes capture-precision item #11 (specced, never executed). Do not retry until
it passes.
