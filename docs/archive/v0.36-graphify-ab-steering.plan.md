## 1.1 Graphify's real setup surface (researched 2026-07-28)

**Do not hand-write a steering block.** Graphify ships its own installers, and
the test must use them — otherwise we'd be measuring *my guess* at what graphify
installs rather than what a real user gets. Verified from graphify's CLI
reference:

| command | what it installs | relevant to |
|---|---|---|
| **`graphify claude install`** | **`CLAUDE.md` steering + a `PreToolUse` hook** | **claude — arm B** |
| `graphify codex install` | `AGENTS.md` | codex (removed from cage) |
| `graphify opencode install` / `claw install` / `droid install` | `AGENTS.md` | other assistants |
| `graphify hook install` / `uninstall` / `status` | git post-commit + post-checkout **graph rebuild** | graph freshness — *not* agent usage |

Each installer has a matching `uninstall`.

**Corrected on contact (G0.5, 2026-07-28, against the installed `graphifyy
0.5.0`):** no `--strict` mode exists anywhere in this version — confirmed by
reading the installed package's own argument parsing
(`graphify/__main__.py`: `claude install` takes zero arguments). The
"secondary docs" reference above does not hold for the installed binary;
there is nothing to defer to G1. Also: **`graphify claude install` has no
per-subcommand `--help`** — appending `--help` does not print help, it *runs
the installer for real* (idempotently safe only if `CLAUDE.md` already
carries the `## graphify` marker; unsafe otherwise). Top-level `graphify
--help` is the only safe discovery surface. Full provenance:
`cage-lab/golden/workspace/SETUP.md`.

**Also corrected: the PreToolUse hook `graphify claude install` writes never
invokes the `graphify` binary at all.** It is a static bash conditional —
`[ -f graphify-out/graph.json ] && echo '<hard-coded JSON>' || true` — that
tests the graph file exists and, if so, injects a fixed instructional string
via `additionalContext`, on a `Glob|Grep` matcher. No subprocess named
`graphify` is ever spawned by the hook, so there is nothing here for cage's
PATH-interception `bin/graphify` shim to intercept or bypass. The PATH-bypass
risk in §1.1(a) below is real, but it lives downstream of the hook, not in
it — it applies only if the *agent itself* runs `graphify query|path|explain`
as a shell command per the CLAUDE.md prose. Verbatim hook JSON in
`cage-lab/golden/workspace/SETUP.md`.

### Two consequences that change the experiment

**(a) `graphify claude install` installs a `PreToolUse` hook, not just prose.**
That is a far stronger mechanism than steering — and it introduces a **real risk
worth testing deliberately**:

> cage's `bin/graphify` shim meters by **PATH interception**. If graphify's
> PreToolUse hook invokes graphify by **absolute path** (or via its own Python
> entry point), it **bypasses the shim entirely — the query fires but cage
> records no receipt.**

If that happens, the finding inverts in the most interesting way: *the very
mechanism that makes graphify fire is the one that makes it invisible to cage.*
That would be a HIGH cage finding and a much better explanation for "0 real
receipts" than missing steering. **Arm B must therefore check two things
separately: did graphify fire, and did cage see it.**

**(b) [SUPERSEDED — corrected on contact, G0.5, 2026-07-28] There is no
copilot or kiro installer.** This was wrong: the installed `graphifyy 0.5.0`
top-level `--help` (ground truth, not the docs page this table was built
from) lists first-party installers for **both**:

```
copilot install    copy graphify skill to ~/.copilot/skills (GitHub Copilot CLI)
copilot uninstall   remove graphify skill from ~/.copilot/skills
vscode install      configure VS Code Copilot Chat (skill + .github/copilot-instructions.md)
vscode uninstall    remove VS Code Copilot Chat configuration
...
kiro install         write skill to .kiro/skills/graphify/ + steering file (Kiro IDE/CLI)
kiro uninstall       remove skill + steering file
```

So the always-on list is **claude, copilot (+ vscode), kiro, codex, opencode,
claw, droid, trae, trae-cn, antigravity, hermes** — not the five originally
listed, and not missing copilot/kiro. Revised:

- **V2 (claude + graphify)** tested with `graphify claude install` (unchanged
  — this is what G0.5/G1 build and run).
- **V4 (copilot + graphify)** now **does** have a first-party path —
  `graphify copilot install` (CLI, `~/.copilot/skills`) or `graphify vscode
  install` (VS Code Copilot Chat, `.github/copilot-instructions.md`) — a
  *skill*, not a `CLAUDE.md`-equivalent block or a `PreToolUse`-equivalent
  hook. Whether Copilot's skill-invocation model creates the same
  PATH-interception risk as claude's hook is untested and is now a real
  question for whichever arm exercises V4, not an assumption to carry
  forward.
- **V5b (kiro + graphify)** likewise has `graphify kiro install` (writes
  `.kiro/skills/graphify/` + a steering file) — untested here.

**Neither correction changes G0.5/G1's scope** (claude only, `graphify claude
install`, no paid calls) — it only invalidates the "asymmetry" framing below
for whoever scopes a future copilot/kiro arm. Not exercised, not installed,
not verified beyond reading `--help` — a claim about what these installers
*do* would need the same discovery-before-execution treatment G0.5 gave
`claude install`.

~~That asymmetry is itself a finding for the field matrix: **graphify's
always-on integration exists for one of cage's three agents.**~~ — false as

## 1.2 Rebuilding the workspace cleanly (Arpit: "maybe dump it and recreate")

The instinct is right — **the workspace's provenance is unknown**, which is the
actual defect. `graphify-out/` exists but nobody recorded *how* it got there, and
`graphify claude install` was evidently never run. A corpus captured against a
workspace nobody can reproduce is weak evidence.

**But "dump it" must be scoped, because three different things live in there and
only one is disposable:**

| thing | verdict | why |
|---|---|---|
| `golden/workspace/` — the frozen scratch repo | **REBUILD its config layer only** (§1.2.0) | Unknown provenance is the defect — but the *fixture bytes* are arm A's control and must survive untouched |
| `golden/runs/` — per-run scratch (venv, scratch HOME) | **DELETE freely** | Disposable by design, gitignored |
| `golden/captures/` — the raw captured logs | **KEEP** | They are arm A's evidence — not *wrong*, just a now-*known* condition (graphify present, never installed). Deleting them destroys the only baseline arm B is compared against |
| `cage/docs/regression/**` — published hashed reports + finding docs | **NEVER DELETE** | Published evidence, hashed, append-only. This is the line that does not move |

So: **rebuild the workspace, keep the evidence.** Dumping the captures would
throw away the very baseline that makes arm B meaningful, and dumping the
published reports would break the audit chain we just built.

### 1.2.0 The correction the rebuild plan needed: **preserve the fixture bytes**

A naive "dump and recreate" **destroys the A/B**. Arm A's captures were taken
against a specific toy codebase; if arm B runs against a freshly-authored one, the
token delta A−B measures *"different repo"* as much as *"graphify installed"* —
a confound that would invalidate the very comparison the rebuild exists to enable.

So the rebuild is **layered, not total**:

| layer | action | why |
|---|---|---|
| **Fixture** — the toy package's source files, `.gitignore`, fixture content | **PRESERVE byte-for-byte** (hash before, hash after, assert equal) | It is the independent variable's *control*. Changing it confounds A vs B |
| **Tooling** — `graphify-out/`, `CLAUDE.md`, `.claude/`, `.cage/`, `bin/` | **DELETE and re-derive** via the tools' own installers | This is the layer with unknown provenance — the actual defect |
| **Git history** | re-init is fine | Not read by the experiment |

Stated as a rule: **rebuild the configuration, never the corpus.** If the fixture
genuinely must change, that is a *new baseline* — arm A must be re-run, and the old
captures are relabelled, never silently compared against.

**Also: `graphify hook install` is deliberately OUT of scope for the rebuild.** It
rebuilds the graph on commit — graph *freshness*, not agent *usage* — and a
mid-run rebuild would add noise to the one thing arm B measures. Install it later,
if ever, and never during a capture.

### 1.2.1 The rebuild, with provenance recorded

Recreate `golden/workspace/` from scratch, and this time **record every command
that made it** in `workspace/SETUP.md` (+ a re-runnable `workspace/rebuild.sh`),
so the setup is reproducible rather than archaeological:

```
0. hash every fixture source file            # the control — must be identical at the end
1. git init, fixture files PRESERVED as-is   # never re-authored (§1.2.0)
2. graphify <build verb>       # produce graphify-out/ — record the exact verb+flags
3. graphify claude install     # CLAUDE.md steering + PreToolUse hook  ← was MISSING
4. (SKIPPED: graphify hook install — commit-time graph rebuild adds capture noise, §1.2.0)
5. cage setup --claude         # .cage/, cage.toml [sources], bin/graphify shim, MCP
6. cage doctor                 # interceptor LIVE, not merely present
7. re-hash the fixture         # assert byte-identical to step 0, or the A/B is void
```

**Step order matters and must be recorded:** if `cage setup` runs before
`graphify claude install`, graphify's installer may rewrite `CLAUDE.md` and drop
cage's block (or vice versa). **Which tool clobbers which is itself worth
observing** — it is the same shim-vs-steering ownership gap from §4, seen from
the install side. Record what each step did to `CLAUDE.md`.

### 1.2.2 The rule this makes standing

Add to the golden-set plan: **a workspace is only valid evidence if its setup is
reproducible.** Every future workspace carries `SETUP.md` with the exact commands
and their order. A capture against an unreproducible workspace is downgraded to
UNPROVEN — the same standard the benchmark applies to everything else.

## 2. Why the finding is currently over-claiming

The finding's *observation* is true: **unprompted, the agents did not invoke
graphify.** The *implication* people will draw — that graphify savings never
materialise in real use — does **not** follow, because a real graphify-enabled
repo carries the steering block (cage's own does).

This matters beyond tidiness: that implication is the leading candidate
explanation for the 2026-07-22 finding **"0 real receipts across 36,451 calls"**.
If the true cause is *missing steering*, the fix is a `cage setup` improvement
and the mystery closes. If steering is present and it still doesn't fire, the
product finding is real and much more serious. **Right now we cannot tell which**,
and that is the only reason this plan exists.

## 3. The three arms

| arm | condition | what it measures | status |
|---|---|---|---|
| **A — unprompted, not installed** | as run in V2/V4 | do agents reach for an *unadvertised* tool? | ✅ done: **no**, 0 savings rows |
| **B — `graphify claude install`** | run graphify's **own installer** (CLAUDE.md + PreToolUse hook), same question | do agents use graphify when it's installed the way a real user installs it? — *the real-world condition* | ⏳ **G1** |
| **C — driver-invoked** | driver runs graphify itself; compare against arm A's file-reading tokens | what the tool *can* deliver, counterfactual explicit | ⏳ G2, if B is negative **or** copilot/kiro (no installer exists) |

Arm B is the one that was missing, and it must be created **by
`graphify claude install`, not by hand** — the whole point is to reproduce a
real installation.

**Arm B records two independent outcomes, not one:**

1. **Did graphify fire?** (the query ran — check graphify's own output/logs)
2. **Did cage see it?** (a row in `savings/graphify/`)

`fired=yes, cage=no` is the PATH-bypass case in §1.1(a) and is the most valuable
possible result. Conflating the two would hide it.

## 4. Decision tree — what each outcome ships

**G1: graphify fires AND cage records it (savings rows appear):**

- The finding is reframed: *graphify savings require the steering block; without
  it you get exactly zero.*
- Product fix (G4): `cage setup` should **detect `graphify-out/` and ensure the
  steering block exists** — or at minimum `cage doctor` should warn
  "graphify installed + interceptor wired, but no agent steering ⇒ it will
  never fire." Note the asymmetry found in §1: **cage writes the shim; graphify
  writes the steering** — so nobody currently owns the case where one exists
  without the other.
- The A/B becomes measurable: arm A vs arm B is a real token delta.
- **And "0 real receipts" gets a testable explanation.**

**G1: graphify fires but cage records NOTHING — the PATH-bypass case:**

- **HIGH cage finding**, and the best available explanation for "0 real receipts":
  graphify's PreToolUse hook (or its skill/slash path) invokes the binary in a way
  that never traverses cage's PATH shim, so **every real graphify saving on every
  machine has been invisible**.
- Fix direction (not to be built in G1): cage's graphify metering can't rely on
  PATH alone — it needs either a wrapper graphify itself calls, or a
  post-hoc read of graphify's own output. **File it; don't design it inside the
  experiment.**
- This outcome would also retro-explain the 2026-07-22 machine: graphify
  installed, graph present, receipts zero.

**G1: graphify does not fire at all (zero, with the installer run):**

- *Now* the product finding is earned and it is serious: agents ignore an
  explicitly advertised savings tool. That reframes graphify's adoption model
  (and possibly cage's savings story) far more than a config gap would.
- Fall through to arm C so Phase 2 still has an honest measured A−B, clearly
  labelled **driver-invoked**, never presented as organic use.

Either way the finding doc stops saying something it hasn't earned.
