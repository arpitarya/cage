# Handoff: REV-TS — one UTC normal form for every timestamp comparison

**One-liner:** `commitjoin` builds and compares commit windows from raw
`git log %cI` strings (committer-**local** offset) against UTC `…Z` probes, so
every authorship join is skewed by the offset on a non-UTC machine — normalize to
ONE shape at the boundary, keep the string compare.
**Owner / executor:** Claude Code (**Opus** — attribution correctness; a wrong
normal form publishes wrong authorship silently and freezes it into append-only rows).
**Status:** Ready to build. **Nothing blocks it**; it blocks CHATS-AUTHOR (Phase-0
STOP), HR-COPILOT-JOIN and HR-FIELD.

**Design of record:** [proposals/timestamp-utc-normal-form.md](v0.45-rev-ts.proposal.md).
**Sequencing + step detail:** [OPEN-WORK.md](../OPEN-WORK.md) §Implementation, **REV-TS**.
**Both are corrected by this handoff in two places (§5.1, §5.4)** — where they
disagree, this document wins, and the code wins over both.

## 1. Why now

- **Its damage accrues.** Windows recompute at read time and self-heal, but
  `originrecord` freezes rows by `(sha, agent, session_id, method)`. Every sweep
  before the fix writes more permanently-wrong rows that no later fix may rewrite.
- **It is the only machine that has ever run this.** The maintainer's box is IST;
  the published v0.44 dogfood snapshot inherits the skew.
- **A packaged Opus pair is idling on it** — CHATS-AUTHOR's Phase-0 gate STOPs
  until this lands ([chats-author.prompt.md](../chats-author.prompt.md):19–23).

## 2. Definition of done

- [ ] **P0 first, and it must be RED:** a goldenseed repo whose committer dates

- [ ] `commitview._iso` sits on the same parse rather than keeping its own

- [ ] Existing goldens **do not move** (§9.2). Changed golden bytes ⇒ investigate,

- [ ] `just test` full suite 0 fail (from 1401/0, unverified — re-count and correct
      the OPEN-WORK header).
- [ ] CHANGELOG states plainly: pre-fix rows on a non-UTC machine are suspect,

## 3. Scope

**In:** `commitjoin.py` (the helper + build + probes) · `authorcapture.py:107` ·
`commitview.py`'s `_iso` re-point · fixtures + tests · docs/CHANGELOG.

**Out (explicit):** any rewrite, purge, backfill or migration of frozen provenance
rows · invalidating the `_authorship` cursor (§5.4) · CHATS-AUTHOR's `agent%`
column (its own pair) · REV-HARDEN P4's *full-sha-at-write* item (related family,
promote separately — queue-order §7) · the ledger `ts` stamp itself
(`schema._now` is already correct UTC-`Z`) · any other timestamp consumer that is
not part of a window compare (`netsaved`, `verdict`, `study`, `render`, `freshness`
all parse to datetimes and are not string-comparing across offsets).

**The probe shapes, confirmed:** calls stamp `schema._now()` → `…HH:MM:SSZ`
(second precision) or `transcript._epoch_ms_iso` → `…HH:MM:SS.mmmZ`
(**millisecond**); edits carry the Claude transcript's raw `timestamp`
(millisecond `Z`). Window bounds carry whatever offset git stored. So three
precisions and two offset representations meet in one `<` — the bug is structural,
not incidental.

**Why the suite is green:** every goldenseed commit is pinned `+00:00`
([goldenseed.py:424–428](../../tests/goldenseed.py#L424-L428)) and
[test_authorship_capture.py:161–165](../../tests/test_authorship_capture.py#L161-L165)
probes with byte-identical `+00:00` strings. The suite never leaves UTC and never
touches a boundary. It catches none of this.

## 5. Technical approach (decided — do not re-litigate)

### 5.1 The normal form is fixed-precision, and it is SECONDS

**This corrects the proposal's sketch.** Both source docs render
`…THH:MM:SS[.mmm]Z` — *optional* milliseconds. That re-introduces the very bug
being fixed: `"…T10:00:00.000Z" < "…T10:00:00Z"` (`.` = 0x2E sorts below `Z` =
0x5A), so a mixed-precision corpus is still not totally ordered by string compare.
**One precision, always rendered.**

Choose **seconds** — `YYYY-MM-DDTHH:MM:SSZ`, sub-seconds **truncated, not
rounded**:

- `%cI` has **no** sub-second component, so a commit stamped `10:00:00` happened
  somewhere in `[10:00:00, 10:00:01)`. Millisecond precision would push an edit at
  `10:00:00.500` — plausibly *before* the commit — into the next window on false
  precision cage does not have.
- It is the only form that satisfies the module's **own documented contract**:
  *"The upper bound is inclusive: an edit made at the same second as the commit is
  part of it"* ([commitjoin.py:13–14](../../cage/commitjoin.py#L13-L14)). That
  sentence is currently false in code; seconds make it true.
  **[AS BUILT] — this overstated it, and the correction is the load-bearing part.**
  Git renders `%cI` as `…Z` (never `+00:00`) at zero offset, so in a **pure-UTC repo
  the contract already held**, by accident: `.` (0x2E) sorts below `Z` (0x5A), which
  puts a sub-second probe in the earlier window — exactly what an inclusive second
  bound requires. The sentence is false only where a bound carries a non-zero offset.
  That makes the milliseconds option strictly *worse* than a no-op rather than merely
  imprecise: it would have **broken the one case that already worked**. Pinned by
  `test_a_pure_utc_repo_keeps_the_bound_it_already_gets_right`, which is a guard on
  existing behaviour and is labelled as such — not a red-before-green fixture.
- Truncate, don't round — rounding is non-monotone at a boundary and can carry an
  edit across a window it belongs in.
- Nothing needs sub-second: edits are compared to window bounds only, never to
  each other, and `commitview._seconds` measures hours.

### 5.2 Normalize at the boundary, never at the compare

Bounds are normalized once in `commit_windows`; probes once on entry to
`window_for` / `_uncovered`. No compare site does its own conversion — that is how
a second convention gets born.

### 5.3 One parse, two renderings

`commitjoin` owns a private parse (`fromisoformat` on `Z`→`+00:00`; **if naive,
assume UTC**; `.astimezone(utc)`) with two public faces: the string normalizer
(§5.1) and the datetime `commitview._iso` needs for `--since` and `_seconds`.
`commitview` imports rather than keeping its own — that also fixes a latent
`TypeError`: today's `_iso` returns a **naive** datetime for an offset-free input
and comparing it against `ledger.since_cutoff`'s aware cutoff raises. Not live
(git always emits an offset), but it is a trap sitting one input away.

**Unparseable input:** `""` in ⇒ `""` out; garbage in ⇒ `""` out (`window_for`
already treats falsy as no-window). A commit line whose `%cI` will not parse is
**dropped from the window list**, matching the existing malformed-line filter at
[:95](../../cage/commitjoin.py#L95) — fail-open, never a garbage bound.

### 5.4 The frozen rows are NOT repaired, and the cursor is NOT invalidated

**This corrects the queue-order §2.1 step 5, which says only "not rewritten".** The
sharper fact: a corrected sweep does not merely *fail* to fix old rows, it can
**add to them**. `originrecord`'s idempotency key is `(sha, agent, session_id,
method)`, so re-reading a transcript after the fix writes rows on the **corrected**
sha while the wrong-sha rows persist — the same lines then count on two commits in
the repo total.

Two consequences, both deliberate:

- **Do not invalidate the `_authorship` cursor.** A transcript whose bytes are
  unchanged and whose cursor says `covered` is never re-read
  ([authorcapture.py:161–163](../../cage/authorcapture.py#L161-L163)) — leave it that
  way. Forcing a re-read would manufacture the double-presence above.
- **Files still marked uncovered WILL be re-read** and can produce it anyway. That
  is unavoidable without a purge, and a purge is forbidden (append-only law). State
  it in the CHANGELOG; do not paper over it.

A repair verb is **out of scope and should not be invented here.** If it is ever
wanted it is its own proposal, and `cage authorship verify` is report-only and
exits 0, so nothing gates on the inconsistency meanwhile.

## 6. Non-negotiables

- **$0 / stdlib only**; `datetime` only, no new dependency.
- **Determinism law:** no clock, no random; string compare stays; **no datetime
  object enters a stored row**.
- **Fail-open on the capture path** — a bad timestamp yields no window, never an
  exception into `authorcapture`.
- **Method is sacred** — this changes *which sha* a row lands on, never how strong
  the row claims to be. No `method` value moves.
- **Do not touch:** frozen provenance rows · `verbmap` · wiring modules ·
  `schema.py`'s ts stamp · CHATS-AUTHOR's surface.

## 7. Dependencies

None. This is the head of the agent lane (queue-order §8).

## 8. Edge cases & risks

- Repo with mixed local + `+00:00` (GitHub-web/CI) commits → the mis-sort case;
  the fixture should include one. · An amended/grafted out-of-order committer date
  → already handled by the re-sort, which only now sorts a meaningful key. · Empty
  history / no repo / no git → `[]`, unchanged. · A call predating the first commit
  still lands **on** it (open lower bound; `""` sorts below every normalized
  string — keep that property, it is load-bearing). · An edit newer than HEAD stays
  deliberately unrecorded. · `_uncovered` with a truncated-second probe treats an
  edit inside the newest commit's second as **covered**, consistent with the
  inclusive bound — intended, not a rounding slip.

## 11. [AS BUILT] The third deviation: how the invariant became structural

The plan was to normalize bounds in `commit_windows` and rely on discipline
elsewhere. Better was available and is what shipped: **`Window` normalizes its own
bounds**, so a window holding a raw git string cannot be constructed anywhere,
including in a test that hand-builds one (`tests/test_commitjoin.py` does).

One correction to the mechanism: `typing.NamedTuple` **forbids** overriding `__new__`
(`AttributeError: Cannot overwrite NamedTuple attribute __new__`), so `Window` became
a `collections.namedtuple` subclass with `__slots__ = ()`. Same tuple semantics, same
field access, five lines. `_make`/`_replace` bypass `__new__` as they do for every
namedtuple; nothing uses them on `Window`, and the docstring says so.
